# Configuration and operations

No production secrets, provider settings, Firebase rules/indexes or deployments were changed by the stabilization work. The manifests below are **proposals for operator review**, not evidence they have been deployed.

## 1. Server identity and browser origins

| Setting | Purpose / default |
| --- | --- |
| `NODE_ENV=production` | Enables fail-closed production configuration checks. |
| `PORT` | Persistent API defaults to `5050`; standalone socket launcher defaults to `10000`. Servers bind `0.0.0.0`. |
| `JWT_SECRET` | Required in production/Vercel: at least 32 randomly generated bytes. Use the same value on API and socket hosts. Rotation invalidates existing sessions. Never use a sample/test value. |
| `CLIENT_URL` | Public frontend origin, also the backend GitHub OAuth redirect destination. Set explicitly; legacy fallback is `https://devsphere-sj.vercel.app`. HTTPS is mandatory in production. |
| `CLIENT_ORIGINS` | Comma-separated exact origins for CORS/Socket.IO. Falls back to `CLIENT_URL`. Configure each intended production/preview frontend; no wildcard Vercel trust. |
| `V2_ALLOWED_USER_IDS` | Comma-separated **backend user IDs**, not email addresses. Required in production/Vercel to start, approve/reject or deploy runs against the single server-configured repository. Missing list is 503; non-operators are 403. |

Backend sessions expire after **five hours**, use HS256 and require an integer expiration claim. Re-authenticate when expired; socket connections disconnect at expiry. Do not rely on immediate central revocation of an already issued backend JWT: there is no per-token server revocation list. Protect browser-origin execution/XSS because sessions currently use localStorage. For stronger session isolation, migrate to HttpOnly server sessions in a separately reviewed compatibility change.

Firebase ID tokens are verified with revocation checks before backend session issuance. Backend OAuth uses signed short-lived state, an HttpOnly/SameSite cookie and a single-use ten-minute **same-browser frontend nonce**. Start it using the login page's `GitHub via server OAuth` action; the server's `/auth/github` start now requires `client_state`. Raw token fragments without an initiated matching frontend flow are rejected (login-CSRF protection), removed from history and never imported. Successful tokens are also validated through `/auth/me`. GitHub emails do **not** implicitly link an existing password/Firebase account; explicit authenticated account linking/migration is not implemented.

## 2. Firebase Admin and persistence

Use one of:

1. `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` (escaped `\n` is supported); or
2. Google Application Default Credentials with the intended project and restricted service-account IAM; or
3. A **non-production emulator**, with `FIRESTORE_EMULATOR_HOST` and a local project ID. This does not emulate Firebase Auth unless separately configured.

Partial service-account configuration fails unavailable rather than crashing boot. `/api/health` checks actual Firestore reachability and returns 503 without working persistence. An unconfigured app must never be treated as a healthy production deployment just because its HTTP process starts.

All existing server/API Firebase adapters re-export the same initialized backend singleton. If root and server packages are installed separately, resolve SDK diagnostics from the backend package; independent physical copies of Firebase Admin have independent app registries.

### Rules/index review and rollout

- `firebase.json` references `firestore.rules` and `firestore.indexes.json`. No default Firebase project is committed.
- The client has no direct Firestore data queries. Proposed rules deny **all client reads/writes**, including users, projects, proposals, approvals, locks and events. Admin SDK bypasses rules, so restricted IAM and Express ownership checks are still essential.
- V2 history requires the `devsphereRuns` composite index: **userId ASC + createdAt DESC**. Wait until it is ready before accepting users. The in-memory test double does not validate hosted indexes/rules/IAM.
- Large unqueried source, event, chat and post fields have index exclusions to avoid excessive index fanout. Review against any consumers outside this repository before applying them.
- An authorized operator may use Firebase CLI with an **explicit intended project ID** to deploy only reviewed rules/indexes. Do not replace a shared production project's rules without checking other applications. No such command was executed here.
- Back up existing data; review case-normalized email uniqueness/index migration (`userEmails`) for legacy accounts. Never merge accounts just because emails match.

V2 run documents are capped below Firestore's 1 MB limit, hold at most 100 recent events and keep immutable proposal/hash bindings. History reads the newest 30 (max 50) records. A durable owner lease prevents concurrent run/approval execution; new runs are limited to five per owner per minute. Leases expire after five minutes. A crashed `executing`/unknown mutation is **not** an automatic retry grant. Audit and inspect provider state before operator reconciliation.

Projects use versioned file saves: include the latest integer `version`; a concurrent stale save returns 409. Reload and merge local edits manually rather than blind overwrite. Projects allow at most 100 files/600 KB source; chat retains at most 30 entries and a 200 KB byte budget. Post mutations are transactional and respect document byte limits. Keep backups and define retention/cleanup for runs, provider events, quotas and local Git caches; automatic archival is not supplied.

## 3. AI providers and budgets

| Setting | Meaning / bounds |
| --- | --- |
| `OPENAI_API_KEY` | Required for V2 Responses API requests. Never shared with the client. |
| `OPENAI_MODEL` | Default `gpt-4.1-mini`; must support Responses API strict JSON-schema output. Verify live access before rollout. |
| `OPENAI_TIMEOUT_MS` | Per attempt: default 30,000; accepted 1,000–60,000. |
| `OPENAI_MAX_RETRIES` | SDK retries: default 1; accepted 0–2. |
| `OPENAI_MAX_OUTPUT_TOKENS` | Developer stage: default 8,000; accepted 1,000–12,000. Intent/plan caps are 1,500/2,500. |
| `RUN_TIMEOUT_MS` | Shared provider abort budget: default 180,000; accepted 5,000–240,000. |
| `GEMINI_API_KEY` | Existing editor, scaffold, resume and local Git-review features. Independent of OpenAI. |
| `GEMINI_MODEL` | Default `gemini-2.5-flash`; verify actual model availability. |
| `GEMINI_TIMEOUT_MS` | Per-request AbortSignal: default 30,000; accepted 1,000–60,000. Output capped at 8,192 tokens. |

V2 uses `store:false`, bounded context, schema validation and persisted **reported** usage when available. Invalid/incomplete/refused/oversized or timed-out output fails instead of becoming a placeholder proposal. Credential-like or configured-secret-bearing V2 context is rejected before the OpenAI call. Detection is heuristic, not a complete DLP guarantee; never submit secrets or sensitive source without an approved data-handling policy. Legacy Gemini prompts also contain private project/resume data; provider consent, retention and privacy review remain operator responsibilities.

Resume uploads: PDF/TXT only, 2 MB multipart input and 60,000 extracted characters. PDFs run in a separate worker with a ten-second deadline, 20-page cap, 128 MB V8 old-heap setting and at most two active workers **per process**. Worker limits are not a native-memory/container security boundary: deploy OS/container memory/CPU limits and edge upload/rate controls. The code runner calls the external Wandbox service with a 20-second budget, supports its configured five compiler IDs only, and reports unavailable/unsupported compilers rather than substituting another language.

## 4. GitHub repository and native Git

| Setting | Meaning |
| --- | --- |
| `GITHUB_REPOSITORY` | Exact `owner/repository`; target default branch is discovered dynamically. |
| `GITHUB_TOKEN` | Least-privilege contents/PR write, metadata/read, checks/status read and branch-protection read for the intended repository. A GitHub App installation token is preferable. |
| `GITHUB_TIMEOUT_MS` | Per request: default 15,000; accepted 1,000–30,000. |
| `GITHUB_MAX_RETRIES` | Retryable **reads only**: default 1; accepted 0–2. Mutations never automatically retry. |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_REDIRECT_URI` | Optional separate **backend OAuth** sign-in; callback must match the registered public `/api/auth/github/callback` URL. Firebase GitHub popup sign-in is configured in Firebase independently. |
| `GIT_CACHE_DIR` | Optional isolated cache for the legacy local-commit feature. Production defaults to the OS temp directory; development uses ignored `server/git-cache`. |

Protect the live default branch. Configure required status checks through the branch-protection API with trusted app identities (e.g. the actual GitHub Actions check). Applicable branch rulesets and legacy protection are both discovered. Missing/inaccessible definitions or unsupported workflow/deployment rules safely **block successful CI verification and skip deployment**. CI is read-only, uses SHA-pinned Node-24 action runtimes, and runs the application checks on Node 22.22.3. Full Auto only opens a PR; it does not authorize merge or production deployment.

Generated writes are limited to 20 files/400 KB proposal content, permitted paths and canonical text/blob data. Base/head/blob conflicts require a fresh proposal and approval. A default branch advancing after approval or during execution blocks stale PR creation. A network timeout can leave an isolated branch/commit at GitHub; consult recorded evidence and GitHub before retrying. There is no rollback of already confirmed isolated commits and no automatic reconciliation of an ambiguous mutation.

Legacy local commits are not GitHub pushes. They run serially per project in their own `.git`, use isolated Git configuration/HOME, reject active hooks, unsafe legacy configuration, symlinks and linked metadata, and never inherit this application's parent checkout. Quarantine any pre-existing unsafe cache instead of relaxing checks. Install native Git on persistent hosts; ephemeral/serverless cache history is not durable product storage. Cross-process local-cache locking is not implemented: do not share this directory between independent instances.

## 5. Sockets and signed provider webhooks

- Prefer one persistent process for API + Socket.IO. The standalone launcher is `node socket-server/server.js` and uses shared backend modules/dependencies; install root/server dependencies, not just the dependency-free launcher package.
- `REDIS_URL` enables adapter/emitter relay between API/serverless and persistent socket processes. Use private/TLS Redis, shared JWT/CORS settings and sticky sessions when polling across multiple socket nodes. Verify actual pub/sub delivery and recovery before claiming a multi-instance deployment works.
- User data is sent to authenticated `devsphere:user:<id>` rooms, never global broadcasts. Client-supplied room IDs cannot join another user's reserved room. Collaboration additionally rechecks workspace membership on each mutation. Multi-node presence aggregation is not implemented; presence is local to a socket process.
- `GITHUB_WEBHOOK_SECRET` and `VERCEL_WEBHOOK_SECRET` are independent shared provider secrets. Configure the provider to send exact signed bytes to `/api/webhook?projectId=<id>`.
- A workspace owner/operator first saves a repository mapping via `/api/webhook/configuration`; it must match `GITHUB_REPOSITORY`. Invalid/missing signatures, another repository, unknown projects and duplicate body deliveries never execute agents or GitHub mutations.
- Provider events are evidence, not synthetic errors or successful fixes. Failure cards link to a **new explicit V2 intent**. The old autonomous webhook mutation shortcut has intentionally been removed.

General HTTP rate limits are process-local (V2 run/approval execution leases and new-run quotas are durable). Enforce deployment-wide IP/user quotas, request deadlines and abuse controls at the ingress. Never broadly trust user-supplied forwarding headers. The Vercel adapter trusts its single hosting proxy hop; configure any other reverse proxy only after reviewing the actual topology.

## 6. Vercel deployment and recovery

`VERCEL_API_TOKEN`, `VERCEL_PROJECT_ID` and numeric `VERCEL_GITHUB_REPO_ID` are required for the explicit post-merge deploy action; optional `VERCEL_TEAM_ID` and `VERCEL_PROJECT_NAME` select the team/name. `ENABLE_PRODUCTION_DEPLOYMENTS=true` must be set **only after separate owner authorization**. It is not enabled by this branch. `VERCEL_TIMEOUT_MS` defaults to 15,000 (1,000–30,000); the shared `DEPLOYMENT_TIMEOUT_MS` defaults to 60,000 (5,000–120,000).

The server verifies the merged PR's original delivered head, actual repository/current default branch, unchanged merge SHA and required CI before issuing one production creation request. Vercel `QUEUED`/`INITIALIZING`/`BUILDING` remain pending; `ERROR`/`CANCELED` are failed; only `READY` plus a provider URL is deployed. Creation responses must belong to the configured Vercel project; a mismatched response is unknown, not successful. A known pending deployment is refreshed by ID and project ownership is verified. A later audit/status-read failure preserves that ID/outcome and cannot authorize another creation.

**Unknown/ambiguous creation:** stop and reconcile manually in Vercel. Do not change a run back to `pull_request`, delete its deployment ID, blindly click retry or restart an executing mutation to obtain another deployment. If the process dies between provider creation and durable recording, the run remains held/unknown for manual investigation. No automatic recovery endpoint is provided.

`vercel.json` serves the Vite SPA and adapts `/api/*` to the existing Express ESM app; function maximum duration is 300 seconds and raw webhook bodies are preserved. Confirm plan limits and inclusion of worker/PDF assets during a real preview build. Vercel's own Git integration can independently auto-deploy PRs/default-branch pushes: configure its policy separately to avoid bypassing application deployment gates or creating duplicates. Creating this stabilization PR does not authorize any production deployment.

## 7. Release checklist

1. Review this branch, dependency advisories and CI on its exact commit. Do not merge your own PR automatically.
2. In an isolated authorized repository/project, verify real Firebase identity, owner isolation, indexes, transactions, rules and persistence across restarts.
3. With budget-limited credentials, run Manual, Approval (including stale/duplicate/racing approvals), Assisted and Full Auto against actual Responses API/GitHub providers. Inspect real generated code and actual target CI.
4. Verify socket expiry/reconnect, notifications/deep links and, if used, Redis across distinct API/socket processes. Test a real browser, not only JSDOM.
5. Obtain separate explicit authorization for any test merge/deployment. Only then verify an actual merged default-branch CI commit, one Vercel creation, pending refresh and real READY/error outcomes.
6. Configure ingress limits, backups/retention, monitoring, provider spend alerts, OS worker limits and manual ambiguous-operation recovery. Resolve or explicitly accept remaining upstream advisories under your security policy.

Until these external checks complete, production release remains **BLOCKED**, not implicitly approved by local mocks or a green frontend build.

`qa.execution` contains protocol, digest, actual command exits/durations, bounded
output summaries and cleanup state. Only `sandbox-v1` complete passing evidence
can satisfy the central Decision Engine or transactional approval/deployment
claim. Old static approvals must be regenerated, not edited in Firestore.

PR check refresh is once per run per minute, transactionally reserved across
instances. Every observation records its SHA/time; successful observations older
than five minutes are served as stale. Provider quotas also bound refresh across
many runs. History shows current evidence, not perpetual assurances.

`POST /api/v2/runs/:id/cancel` is owner/operator-only and cooperative. Active
workers check durable cancellation every two seconds and before GitHub stages;
provider calls and the QA service receive abort signals. Cancellation cannot undo
accepted writes. If a worker died, a cancellation request alone cannot confirm
cleanup or absence of provider mutations. Reconcile manually before retrying.

Request IDs are durable single-use owner-scoped deduplication keys. A duplicate
returns 409 with the existing run ID, not a second execution. Provider timing and
attempt metadata omit URLs, headers and bodies. Only the latest 100 metrics and
100 events are held in a run; long-term audit retention requires an operator sink.

New collections: `devsphereRunRequests` (request ID hash → original run) and
`devsphereProviderQuotas` (owner/provider hash → minute counter). Existing deny-all
client rules already cover them. New `devsphereRuns.ci`/`providerMetrics` index
exemptions are operator-reviewed optimizations, not deployed changes. See the
[release and operations checklist](PRODUCTION-READINESS.md) for explicit project
selection, retention, backup, recovery and rollback.

### Troubleshooting `/api/auth/user` synchronization failures

Firebase sign-in in the browser and backend session/profile synchronization are
separate steps. A verified browser identity does not establish an application
session until the Admin SDK verifies it (including revocation) and the profile
read/write succeeds. Do not disable revocation checks or loosen Firestore client
rules to work around a backend error; Admin access uses IAM, not those rules.

A synchronization failure now returns a **string** `error`, a stable application
`code`, and a `requestId`. Invalid/expired/revoked identities return 401
(`INVALID_FIREBASE_TOKEN`); provider/Firestore availability failures return 503
(`AUTH_SYNC_UNAVAILABLE`). Numeric Firestore/gRPC codes are handled without
throwing a secondary error from the error handler. The login UI also accepts
upstream `{error: {code, message}}` responses without rendering an object.

Match the response `requestId` to the server log entry
`Authentication synchronization failed`. It contains only `stage` and an
allowlisted `providerCode`, not tokens, emails, raw provider errors or secrets:

- `verify-token`: verify that browser Firebase configuration and Admin project
  selection match, the Admin identity has the required Firebase Auth permissions,
  and provider connectivity is available. Invalid user tokens still require a
  fresh sign-in; no backend session is issued on failure.
- `read-profile`, `create-profile`, `update-profile`: inspect the explicitly
  selected Firestore database and the deployed Admin service account's IAM.
  gRPC `7` means permission denied; `14` means unavailable; `4` means deadline
  exceeded. Fix the actual cause rather than treating it as a bad password.
- `sign-session`: inspect server-only session-signing configuration.

The absence of a configured Admin app/database or JWT secret is separately
reported as 503 before synchronization begins. After deploying this fix, capture
only the HTTP status, application code, request ID and the corresponding safe
stage/provider code for diagnosis. Never share the `idToken`, Authorization
header, private key or complete unredacted network request. Local regression tests
mock provider failures; they do not establish the cause of a hosted outage.
